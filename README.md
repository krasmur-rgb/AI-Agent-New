# Planner → Agent → Evaluator

Маленькая продуктовая команда из AI-агентов по схеме из выступления Anthropic про агентов,
которые могут работать часами. Построена на [Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview).

```
запрос → planner → [ contract ⇄ ] → agent (builder) → evaluator (Playwright) → fix → …
```

## Как это устроено

Три роли. У каждой — **свой контекст** (отдельный вызов `query()` Agent SDK), свой системный
промпт, свой набор инструментов и своя зона ответственности. Роли не делят состояние диалога —
они общаются только через файлы на диске (markdown и JSON).

### 1. Planner — верхний план и спринты

Получает короткий запрос и превращает его в структуру работы: что собираем, какие большие части
нужны, в какой последовательности, какие спринты должны получиться.

Ключевая деталь: planner **не расписывает техническую реализацию заранее**. Если в начале
придумать подробный план на 200 шагов и ошибиться, ошибка поедет каскадом через часы работы.
Planner держит уровень продукта и спринтов; технические решения остаются за builder'ом,
ближе к моменту реализации.

Артефакты: `plan.md`, `sprints.json`.

### 2. Contract — договорённость о «готово» до начала работы

Главный механизм всей системы. Перед сборкой спринта builder и evaluator согласуют **contract** —
список конкретных проверяемых утверждений:

- builder пишет `contract-draft.md`: «я соберу такую фичу, проверять её надо вот так»;
- evaluator отвечает: «добавь такой сценарий, такой edge case, проверку сохранения при перезагрузке»;
- они обмениваются markdown-файлами, пока evaluator не одобрит (`contract-review.json`);
- на последнем раунде evaluator дорабатывает контракт сам, чтобы переговоры гарантированно завершились.

Дальше evaluator проверяет не расплывчатый исходный запрос, а этот контракт. Расплывчатые
критерии дают расплывчатую критику; конкретные — точную проблему, которую builder может починить.

Артефакт: `contract.md`.

### 3. Agent (builder) — сборка спринта

Собирает фичу так, чтобы прошёл **каждый** критерий контракта. Все технические решения — его:
стек, структура файлов, архитектура. Инструменты: Read/Write/Edit/Bash/Glob/Grep.

### 4. Evaluator — жёсткая проверка через браузер

Отдельный агент-критик со своим контекстом и явно адверсариальной инструкцией: отдельного
критика проще настроить быть жёстким, чем заставить builder'а честно проверять самого себя.

Evaluator поднимает HTTP-сервер, открывает приложение через Playwright (Chromium), кликает по
интерфейсу, делает и **просматривает** скриншоты, ловит ошибки консоли страницы — и выносит
вердикт по каждому критерию контракта. Критерий без прямых доказательств считается проваленным.

Артефакты: `critique-N.md` (что и как воспроизвести), `verdict-N.json`, `screenshots/`.

### 5. Финальный цикл

```
1. planner разбивает задачу на спринты
2. builder берёт следующий спринт
3. builder и evaluator согласуют contract          (до CONTRACT_ROUNDS раундов)
4. builder строит
5. evaluator проверяет через браузер
6. builder чинит по критике
7. пункты 5–6 повторяются                          (до FIX_ITERATIONS итераций)
```

Качество держится не на «модель умная», а на архитектуре процесса.

## Запуск

Требования: Node 18+, доступ к Anthropic API (`ANTHROPIC_API_KEY` или профиль `ant auth login` /
окружение Claude Code), Chromium для Playwright (`npx playwright install chromium`, если не предустановлен).

```bash
npm install
npm run smoke                      # быстрая проверка, что SDK и авторизация работают
npm start -- "сделай retro game maker"
```

Результаты:

- `workspace/<slug>/` — собранный продукт (открывается статическим HTTP-сервером);
- `runs/<timestamp>-<slug>/` — все артефакты процесса: план, контракты, ревью, критика,
  вердикты, скриншоты, `summary.json`.

## Настройка

Через переменные окружения:

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `MODEL` | `claude-opus-4-8` | модель для всех ролей |
| `PLANNER_MODEL` / `BUILDER_MODEL` / `EVALUATOR_MODEL` | `MODEL` | модель конкретной роли |
| `CONTRACT_ROUNDS` | `3` | раундов согласования контракта |
| `FIX_ITERATIONS` | `3` | циклов build → evaluate → fix на спринт |
| `*_MAX_TURNS` | см. `src/config.ts` | лимит шагов агента на фазу |

Пример дешёвого прогона:

```bash
MODEL=claude-sonnet-5 CONTRACT_ROUNDS=1 FIX_ITERATIONS=2 npm start -- "одностраничный счётчик с localStorage"
```

## Структура кода

```
src/
├── index.ts         # CLI-вход
├── orchestrator.ts  # финальный цикл (спринты → contract → build → evaluate → fix)
├── planner.ts       # фаза планирования
├── contract.ts      # переговоры о контракте между builder и evaluator
├── builder.ts       # фазы BUILD и FIX
├── evaluator.ts     # фаза браузерной проверки (Playwright)
├── prompts.ts       # системные промпты трёх ролей — ядро паттерна
├── agent-runner.ts  # обёртка над query() Agent SDK: роль = контекст + промпт + инструменты
├── config.ts        # модели и лимиты
└── types.ts         # Sprint / ContractReview / Verdict
```

## Примитивы из выступления → как реализовано здесь

| Примитив | Реализация |
|---|---|
| subagents для отдельных ролей | отдельный `query()` на роль со своим системным промптом и контекстом |
| Playwright / Chrome для проверки UI | evaluator пишет и запускает Playwright-скрипты через Bash, читает скриншоты |
| skills / rubrics для критериев качества | contract-файлы: список проверяемых критериев вместо расплывчатого запроса |
| auto mode / permissions для автономной работы | `permissionMode: "bypassPermissions"` + ограниченный `allowedTools` на роль |
| contract files | `contract-draft.md` ⇄ `contract-review.md` → `contract.md`, вердикты в JSON |

# «Анна Каренина» — интерактивная драма (статический сайт для GitHub Pages)

Русскоязычная интерактивная нарративная драма по арке Анны. Игрок ведёт Анну
через 5 актов; выборы невидимо копят «тягу» к одному из 5 русел-финалов.
Полностью статический детерминированный сайт: вся логика в браузере, никакого
рантайм-ИИ и серверного кода. Спецификация — в `SPEC.md` (раздел механики,
актов, палитры).

## Структура сайта

```
index.html              каркас страницы
css/style.css           все стили (книжная палитра, адаптив)
js/
  engine.js             движок: состояние, тяга, переходы, финал (точка входа)
  render.js             отрисовка сцены, картинки, выборов, модалок
  comments.js           заметки отладчика + выгрузка
data/scenario_data.json ВСЕ сцены, выборы, векторы, финалы (текст правится тут)
img/desktop/            широкие 3:2 — I-1.jpg, IV-1-LF.jpg, fin-L.jpg …
img/mobile/             вертикальные кропы ~4:5 — те же имена
.nojekyll               пустой файл — обязателен для GitHub Pages
```

Данные отделены от кода: движок читает `data/scenario_data.json` через `fetch`.
Тексты сцен **не вшиты** в JS — автор правит JSON без программиста.

## Механика (кратко; полностью — SPEC §3–4)

- 5 русел = 5 финалов: **L** любовь, **C** клетка, **R** отречение, **F** руины, **X** рельсы.
- Асимметричная инерция (`applyVec`, константы `STICK=0.4`, `VISC=0.4` в начале
  `js/engine.js`): ход `down:true` — полный вес + липкость (−STICK у C и R);
  ход `down:false` — вес × VISC.
- Лидер = максимум тяги среди живых русел; `kills` закрывают финалы навсегда.
- Акт IV ветвится по лидеру на входе (**F идёт по ветке L**). Акт V сходится,
  сцена V.1 берёт текст из `proseByRiver` по лидеру. Финал — по лидеру среди
  живых, без выбора концовки.

## Локальный запуск

Открывать через локальный HTTP-сервер (движок грузит JSON через `fetch` —
просто открыть `index.html` файлом не сработает из-за CORS):

```bash
cd /путь/к/репозиторию
python3 -m http.server 8000
# затем открыть http://localhost:8000/
```

Альтернатива без Python: `npx serve .` или любой статический сервер.

## Режим отладки

Переключатель «режим отладки» вверху (по умолчанию **включён**). Показывает под
каждым выбором его вектор/kills/природу, панель тяг с лидером, служебные строки
в развязках и финале, а также поля заметок под каждой сценой. Снять галочку —
чистый режим конечного игрока. Заметки хранятся в памяти (не в localStorage);
кнопка «Выгрузить все заметки» собирает их по порядку сцен вместе с путём.

## Включение GitHub Pages

1. Закоммитить все файлы сайта в корень репозитория, запушить в ветку.
2. Убедиться, что в корне есть пустой файл **`.nojekyll`** (иначе Pages может не
   отдавать папки `js/` и `css/`).
3. **Settings → Pages → Source:** Deploy from branch → выбрать ветку и `/ (root)`.
4. Приватный репозиторий на платном тарифе: Pages-сайт по умолчанию требует
   аутентификации GitHub. Чтобы тестировщики без аккаунта могли открыть —
   в **Settings → Pages** выставить visibility сайта **Public** (исходный код
   остаётся приватным).
5. Дождаться сборки (значок в Actions / вкладка Pages покажет URL вида
   `https://<user>.github.io/<repo>/`).

### Про кеш

Pages кеширует агрессивно. При замене картинок или данных — версионировать имя
файла (`scenario_data.json?v=2`) или переименовывать файл, чтобы обойти кеш.

## Картинки

Каждая сцена показывает картинку сверху: `img/desktop/{код}.jpg` (≥768px) и
`img/mobile/{код}.jpg` (<768px). Имя = код сцены, точки → дефисы (I.1 → `I-1.jpg`,
IV.2-LF → `IV-2-LF.jpg`, финалы → `fin-L.jpg`…`fin-X.jpg`). Ветки C/R/X Акта IV
на старте используют `placeholder-C/R/X.jpg`. **Если файла нет — показывается
нейтральная заглушка** (тёмный градиент + код сцены), не битая иконка: сайт
полностью работает и без картинок.
