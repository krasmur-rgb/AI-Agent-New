маленькая продуктовая команда из агентов

Planner → Agent → Evaluator

Три ИИ-агента с разными ролями собирают продукт по спринтам. У каждого — свой контекст и своя зона ответственности; общаются они только через файлы на диске. Красным отмечено, где в это можешь вмешаться ты.

  • Planner— план и спринты
  • Agent / Builder— собирает
  • Evaluator— строгий критик
  • Ты— точки участия
Ты
Вход

Короткий запрос

Одна фраза: что собрать. Чем конкретнее ты можешь описать «что кликнуть и что должно произойти», тем лучше сработает вся схема.

Planner

Разбивает на спринты

Держит уровень продукта: что собираем, какие большие части, в каком порядке. Не расписывает техническую реализацию — ранняя ошибка в детальном плане поехала бы каскадом через часы работы.

Evaluator

Ужесточает

Добавляет edge-кейсы, пустые состояния, проверку «переживёт ли перезагрузку». Одобряет, когда критерии airtight.

Builder

Строит спринт

Реализует так, чтобы прошёл каждый критерий контракта. Инструменты: чтение, запись, правка файлов, запуск команд.

Evaluator

Проверяет в браузере

Поднимает сервер, открывает приложение через Playwright, кликает по интерфейсу, снимает и смотрит скриншоты, ловит ошибки консоли. Критерий без доказательства = провал.

Развилка

Прошёл контракт?

Да → следующий спринт.  Нет → builder чинит по критике, и цикл повторяется (до лимита итераций).

Итог

Готовый продукт + весь след процесса

Собранное приложение в workspace/, а рядом — план, контракты, критика, вердикты и скриншоты в runs/. Это не только результат, но и отладочный след.

Где ты участвуешь

Схема автономна, но у неё есть пять дешёвых точек вмешательства. Самая важная — вторая.

  1. до запуска
    Формулируешь запрос.

    Проверь себя: сможешь перечислить, что кликнуть и что должно произойти? Если нет — задача либо не для этой схемы, либо её надо доформулировать.

  2. до сборки ★
    Читаешь contract.md.

    Здесь сидит почти весь рычаг качества. Одна правка критерия до сборки экономит часы фиксов после: расплывчатый критерий → расплывчатая критика, конкретный → точная проблема.

  3. настройка
    Задаёшь модели и лимиты.

    MODEL, CONTRACT_ROUNDS, FIX_ITERATIONS — черновик дёшево (Sonnet, короткий цикл), чистовик дорого (Opus, полные лимиты). Модель можно задать по ролям.

  4. после
    Смотришь артефакты.

    Если спринт завис на лимите — диагноз почти всегда в critique.md и скриншотах: контракт требовал невозможного, или builder не смог починить конкретный критерий.

  5. в любой момент
    Останавливаешь прогон.

    Каждая роль — полный агент, и всё это реальные токены с твоего аккаунта. Остановка не теряет уже собранное — артефакты остаются на диске.

Почему это работает

Качество держится не на «модель умная», а на архитектуре процесса.

Раздельные контексты

Каждая роль — свой контекст и промпт. Общаются только через файлы. Всё, что должно дойти от builder к evaluator, обязано быть в контракте.

Отдельный критик

Evaluator — независимый агент с адверсариальной инструкцией. Отдельного критика проще держать строгим, чем заставить builder честно проверять себя.

Контракт вместо запроса

Evaluator проверяет не расплывчатый исходный запрос, а согласованный список конкретных критериев. Это создаёт нормальное давление на качество.

Реальный прогон из этой сессии: план на 3 спринта, спринт 1 прошёл цикл собран → 11/12 → починен → 12/12 полностью автономно. Код — в ветке claude/agent-planner-evaluator-pattern.
